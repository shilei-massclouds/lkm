# Agent Instructions

- Do not guess fixes. When investigating a problem, first use reproducible observations to narrow the scope before drawing conclusions or changing code.
- For kernel/runtime/user-mode behavior issues, locate the failing boundary through existing checkpoints, diagnostics, or other reproducible observations before changing behavior. Do not make blind trial fixes from symptoms alone. If existing checkpoints are insufficient, first add or extend a long-term-useful checkpoint/diagnostic, then reproduce and use that evidence to update specs and implementation.
- Treat `Charter -> Model -> Coding -> Impl` as the only core semantic refinement chain. Charter is the human-readable top semantic authority; Model may only formalize and refine Charter; Coding may only constrain Model-to-code mappings such as data structures, algorithms, memory layouts and registers; Impl may only realize their combined effect and cannot reinterpret specifications from existing code.
- Every lower core layer must satisfy all applicable higher constraints. A lower layer may choose a detail only when all applicable higher layers leave it unconstrained. If that choice creates observable behavior, an interface or an object boundary, promote it to the appropriate core specification layer and close downward again.
- Use `charter-first` by default. Before changing files, identify the highest affected core layer, then review Charter, Model, Coding and Impl in that order and record “changed” or “reviewed, no change” for each. Review applicable Compose assembly and Testing validation separately as supporting responsibilities.
- Resolve core conflicts in `Charter -> Model -> Coding -> Impl` order. Guidance, Compose and Testing do not define core semantics; existing implementation, tests, roadmaps and Compose must not override a higher core layer. Coding wins a conflict with Compose. When tests conflict with core specifications, fix the tests or the nonconforming implementation. If Charter intent is unclear or the target conflicts with it, stop and return to a Charter decision.
- Honor `charter-locks.json` before applying `charter-first`: semantic authority and review order are not implicit permission to edit a locked Charter. For a locked Charter, only propose changes unless the user explicitly asks to unlock that exact file.
- For an explicitly authorized locked-Charter edit, use `python3 tools/charter_lock.py unlock PATH`; before ending the task, use `python3 tools/charter_lock.py lock PATH` to refresh the hash and restore read-only mode. An `unlocked` state left by an interrupted task is not authorization for a later agent to continue editing.
- Do not directly `chmod` a locked target, edit its manifest state/hash, remove its visible lock notice, or bypass `make charter-lock-check`. The manifest, lock tool, notice, guidance rules, and build gate are protection mechanisms and must not be weakened to bypass a lock unless the user explicitly asks to change the protection mechanism itself.
- Use `model-first` only when the user explicitly declares the round model-first and supplies the Model adjustment. The agent must not choose the slice. Model-first changes only the modification and confirmation order; Charter remains the final top semantic authority. Record the baseline commit, worktree, relevant behavior and tests, and confirm the baseline repository-root `make test` before editing.
- In a `model-first` round, first modify only Model, run focused validation, and show the actual diff and results to the user. Do not modify Charter, Coding, Compose, Impl, or Testing until the user explicitly confirms the Model change.
- After model-first confirmation, close Charter upward without changing the confirmed Model meaning, ensure Model conforms to Charter, then close Coding and Impl downward and review applicable Compose and Testing responsibilities. If Charter cannot close without changing the confirmed meaning, stop and return to the Model decision. Record the closure outcome of every core layer, keep temporary inconsistency uncommitted, complete all final validation, and obtain explicit authorization before committing.
- Ordinary changes that extend behavior, interfaces, specified object boundaries, or Linux differential semantics must follow one of these named workflows and update applicable core specifications before implementation. The agent must never begin by choosing an implementation slice independently.
- After every code change, run the repository root `make test` as the final regression gate. Focused tests may be used while locating issues, but they do not replace `make test`.
- Run the repository root regression gate as a direct `make test` command. Do not wrap it in `/bin/sh -c`, `/bin/bash -lc`, external pipelines, or shell redirection unless explicitly diagnosing host command-environment issues.
