# Agent Instructions

- Do not guess fixes. When investigating a problem, first use reproducible observations to narrow the scope before drawing conclusions or changing code.
- For kernel/runtime/user-mode behavior issues, locate the failing boundary through existing checkpoints, diagnostics, or other reproducible observations before changing behavior. Do not make blind trial fixes from symptoms alone. If existing checkpoints are insufficient, first add or extend a long-term-useful checkpoint/diagnostic, then reproduce and use that evidence to update specs and implementation.
- Use `charter-first` by default: establish design intent in the charter, then close model, coding, applicable compose, implementation, and testing in that order. Resolve cross-layer conflicts in the same authority order.
- Honor `charter-locks.json` before applying `charter-first`: the layer order is not implicit permission to edit a locked charter. For a locked charter, only propose changes unless the user explicitly asks to unlock that exact file.
- For an explicitly authorized locked-charter edit, use `python3 tools/charter_lock.py unlock PATH`; before ending the task, use `python3 tools/charter_lock.py lock PATH` to refresh the hash and restore read-only mode. An `unlocked` state left by an interrupted task is not authorization for a later agent to continue editing.
- Do not directly `chmod` a locked target, edit its manifest state/hash, remove its visible lock notice, or bypass `make charter-lock-check`. The manifest, lock tool, notice, guidance rules, and build gate are protection mechanisms and must not be weakened to bypass a lock unless the user explicitly asks to change the protection mechanism itself.
- Use `model-first` only when the user explicitly declares the round model-first and supplies the model adjustment. The agent must not choose the slice. Record the baseline commit, worktree, relevant behavior and tests, and confirm the baseline repository-root `make test` before editing.
- In a `model-first` round, first modify only the model, run focused validation, and show the actual diff and results to the user. Do not modify charter, coding, compose, implementation, or testing until the user explicitly confirms the model change.
- After model-first confirmation, close the charter upward without changing the confirmed model meaning, then close coding, applicable compose, implementation, and testing downward. If the charter cannot close without changing that meaning, stop and return to the model decision. Review every applicable layer, modify only affected layers, keep temporary inconsistency uncommitted, complete all final validation, and obtain explicit authorization before committing.
- Ordinary changes that extend behavior, interfaces, specified object boundaries, or Linux differential semantics must follow one of these named workflows and update applicable specifications before implementation. The agent must never begin by choosing an implementation slice independently.
- After every code change, run the repository root `make test` as the final regression gate. Focused tests may be used while locating issues, but they do not replace `make test`.
- Run the repository root regression gate as a direct `make test` command. Do not wrap it in `/bin/sh -c`, `/bin/bash -lc`, external pipelines, or shell redirection unless explicitly diagnosing host command-environment issues.
