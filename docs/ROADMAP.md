# Roadmap

本文是项目唯一的优先级和任务状态入口。其它文档可以保留设计背景、约束、命令和专题方案，但不再维护独立的 P0/P1/P2 计划表。

已确认但尚未闭环的实现缺陷记录在 [`docs/DEFECTS.md`](DEFECTS.md)，不与规划性任务混写。

## 优先级规则

- `P0`：当前最应优先推进，直接影响日常审阅或当前闭环质量。
- `P1`：近期应推进，通常依赖 `P0` 的结果或与其紧密相邻。
- `P2`：后续扩展项，应在当前闭环稳定后推进。

## 当前审计计划：impl 与 Linux 6.12.37 对照

后续回顾检查以当前项目 `impl/` 下由规格驱动生成的代码为对象，以 `~/gitStudy/linux-6.12.37/` 为 Linux 参考源码。审计顺序按 formal model 的阶段树推进，先从 `StartupTimeline` 下的 `BootPhase` 开始，再进入后续阶段。

审计发现问题时，默认先归类并修订规格，而不是直接修改 `impl/` 代码：

1. `model` 规格缺口：Linux 路径中的对象、阶段、状态、事件、依赖、事实或显式 deferred 在 `spec/model` 中缺失或边界不清。
2. `coding` 规格缺口：模型语义已有，但对象到 Rust 实现、目录落点、函数边界、checkpoint/KUnit/smoke 观测或 Linux-like 数据结构约束在 `spec/coding` 中不足。
3. 刻意偏离但未记录：当前实现有意简化或偏离 Linux，但未在 model/coding/roadmap 中记录差异分类、理由和 deferred 边界。
4. 实现偏离已有规格：规格已经明确，`impl/` 代码未遵守；此类问题先记录为生成约束或实现缺口，后续再按规格修正代码。

每个审计项应尽量形成可追踪的 cross-reference：Linux 源码路径、当前 `impl/` 路径、对应 `spec/model` 条目、对应 `spec/coding` 条目、差异分类，以及是否需要新增/修订 checkpoint、KUnit 或 smoke 观测。除非用户明确要求修实现，审计阶段的修改优先落到 `spec/model/**`、`spec/coding/**`、必要说明文档和本 roadmap。

启动阶段逐项审计时，并发/同步控制必须作为固定检查面覆盖：本地中断开关、抢占开关、自旋锁、Mutex、读写锁、RCU、CPU bring-up 同步量、内存/地址转换同步和 TLB/cache flush 边界都要明确判断是否已由 `spec/model` 表达；若 model 已表达但实现映射不清，再修订 `spec/coding` 或生成约束。`impl/` 只作为生成结果和 Linux 对照样本，发现偏差时默认先修规格。

启动子阶段的完成口径统一按 `RestInitPhase` 当前做法执行：先对照 Linux 6.12.37 明确子阶段调用边界和配置裁剪，重点列出锁原语、同步原语、上下文边界、内存顺序和 deferred/trimmed 项；再补齐 `spec/model` 与 `spec/coding`；最后按规格补齐 `impl/arceos_ex`、checkpoint/KUnit/smoke 观测，并执行完整验证。已有完成项保留其当前状态；只有发现某阶段实际只做了最小闭环或局部补强时，才重新标记为待补审核。

本节是当前 P0 的执行清单。每完成一项即更新本节状态并做一次提交；实现变更仍遵循先规格/约束、再代码、再验证的顺序。

### 已确认原则

1. 条件编译选择的是 provider 文件组和链接对象，而不是在同一组 Rust 源码内部做大量细粒度裁剪。默认 provider 仍为 `native`；启用 Linux 路径时选择 `irq-sifive-plic.o + Linux ABI/adaptor shim`，并排除原生 PLIC 对同一硬件的 claim/complete/source enable 接管。
2. 首轮采用简单直接链接方案：`PLIC_PROVIDER=linux-object` 时直接把 `irq-sifive-plic.o` 作为 linker input 传入。静态库封装暂不作为首轮目标；后续若改为 `.a`，必须通过 `--whole-archive` 确保没有全局入口符号的对象文件也会被拉入最终内核。
3. `arceos_ex` 向 Linux PLIC object 的 RISC-V ABI 对齐。当前 Linux `irq-sifive-plic.o` 为 LP64/soft-float ABI，首轮应优先把 `arceos_ex` 切到 soft-float target，例如 `riscv64imac-unknown-none-elf` 或等价 custom target，而不是要求 Linux 对象适配当前 double-float ABI。
4. 上层机制直接向 Linux 形态收敛。Linux object 可见的 initcall section、platform driver、OF/fwnode、irq_domain、irq_chip、chained handler、per-CPU/cpumask 和 lifecycle callback 以 Linux contract 为准；`arceos_ex` 现有对象作为内部承载或 native provider 实现，不再保留一套厚转换后的私有上接口。
5. 下接口按 `nm -u` 逐符号“埋雷”补齐。函数先提供 ABI 正确的兜底实现，默认 panic/fail；全局变量先提供布局和符号名正确的最小对象。只有启动路径实际踩到且功能闭环必须的依赖，才逐项补真实语义；调试、打印、审计、ratelimit 等非关键能力可简化或标记 deferred。
6. 第三方 Linux 二进制对象放入 `impl/third_party/...`，首轮建议路径为 `impl/third_party/linux/6.12.37/riscv64-lp64/`，并保留 Linux 原始相对路径、构建配置和来源说明。
7. 进入下接口排雷阶段后，以已有原生 PLIC/IRQ/UART 近似等价实现为承载基础，优先做小规模 kernel 对齐和薄 shim 补充。若踩到必须新增正式对象、大功能缺失、或方向策略难以判断的问题，应暂停实现推进，先把问题归类并讨论后再继续。

## 下一阶段计划：virtio-rng 与 virtio 基础对象

本节是当前 P0 的执行清单。目标不是完整 virtio 子系统，而是用最简单的真实 virtio 设备 `virtio-rng` 推动可复用的 `virtio-mmio`、virtio core 和 split virtqueue 对象建模与实现。每完成一步必须先检查并确认执行结果，再进入下一步；检查结果应同步到本节状态，必要时同步 `spec/charter/main.md`、`spec/model` 和 `spec/coding/arceos_ex.md`。

### 已确认原则

1. `PlatformDevice` 和 `PlatformDriver` 保持为通用类型/机制边界；`Ns16550aPlatformDriver`、`VirtioMmioPlatformDriver`、`VirtioMmioPlatformDevice`、`VirtioMmioTransportDevice`、`VirtioDevice` 和 `VirtioRngDevice` 是具体实例对象或实例集合。
2. platform bus probe 观测分两层：第一层是通用 driver-core/platform-bus 事实，例如 driver registered、device discovered、match attempted、probe called、probe returned 和 device bound；第二层是具体对象事实，例如 driver/device ref 是否指向 `VirtioMmioPlatformDriver` / `VirtioMmioPlatformDevice`、compatible 是否落在预期集合、MMIO header 是否有效、virtio device id 是否为 `VIRTIO_ID_RNG`。
3. `virtio-mmio` 是普通 platform bus driver，首轮通过 `device_initcall` / platform driver register / OF match / probe 接入现有 `PlatformBus`，不要绕过 platform 总线直接扫描 FDT。
4. `virtio-rng` 首轮只作为真实 virtqueue 数据流闭合验证：提交一个 input buffer、notify、completion、`get_buf len > 0`。不接 hwrng 子系统、不接随机池、不暴露用户态接口，也不判断随机性质量。
5. split virtqueue 首轮只支持 single queue、direct descriptor、`add_inbuf`、`kick`、`get_buf`。packed ring、indirect descriptor、event idx、多队列、完整 DMA API/cache maintenance、reset/remove/suspend/resume 先显式 deferred。
6. 测试分层固定为：对象 API 和纯 fixture 构造走 smoke；真实 QEMU `virtio-rng-device` 链路走 checkpoint/KUnit 只读 observer。checkpoint/KUnit 不直接调用 driver/ring/IRQ action，不伪造 completion。smoke 可以有意构造条件，但不得要求普通对象暴露测试专用 API；历史 `fake_*` / completion injection 接口即使模拟真实外部事件，只要只服务 smoke/KUnit，也必须下沉到 smoke fixture/test harness。
7. 块 I/O 后续按 Linux 层次命名和建模：`BlockReadRequest` / `BlockIoBuffer` 不作为 Linux 对应主对象；真正面向后续 ext2 的对象应是 `Bio`、`BufferHead`、`submit_bio()` / `submit_bio_wait()` 和最小 `blk_mq_submit_bio()` 壳。当前 registry 同步读只是阶段性公开入口，不等同于 Linux 的完整 block layer。
8. 文件系统推进顺序先内存型、再设备命名、再块设备文件系统：先建立最小 VFS 对象和 `ramfs`，再建立 `devfs` 与 `rootfs`，最后回到 `bio` / `buffer_head` 并实现 read-only ext2。这样先丰富 smoke 可见文件系统行为，再让 ext2 接入已有 mount/root/dev namespace 和块 I/O 入口。

## 下一阶段计划：用户态 helloworld 快速路径

若把“尽快加载并运行一个用户态 `helloworld`”作为下一阶段目标，计划调整为先打通最短真实闭环，而不是先补齐完整 Linux 文件和终端栈。当前 ext2 rootfs、VFS path read、virtio-blk、PLIC/UART console 已足够支撑首轮用户态 hello 的输入和输出路径。

优先级调整：

1. `P0` 提升：`PayloadPhase` 的 Linux-like 用户态入口、`UserBootPayload`、`ElfObject`、`UserAddressSpace`、RISC-V U-mode entry/trap、既有 `SyscallException` 下的最小 syscall 分发。
2. `P0` 保留但收窄：rootfs 后命名空间只要求 `/sbin/init` 可从当前 ext2 root 读取；`/dev` remount、完整 mount namespace 和 device file ops 不阻塞首轮 hello。
3. `P1/P2` 后移：page cache、Ext2 indirect block、完整 fd table、TTY/N_TTY、stdin/stdout 文件后端、动态链接、`brk/mmap`、fork/wait/signal。

快速路径任务项：

1. **规格先行：用户态入口对象边界**。新增或补强 `UserBootPayload`、`ElfObject`、`UserAddressSpace`、`UserStack`、`UserTrapFrame`、`SyscallException` / `SyscallTable` 和 `UserInitProcess` 的模型边界；明确 syscall 不新建独立根对象，也不建立独立 `SyscallDispatcher` 对象，而是沿用 `ExceptionStream` 下的 `SyscallException` 分支；明确当前磁盘仍是 whole-disk ext2，`PartitionTable` / `BlockPartition` 不作为首轮前置对象。
2. **构建与磁盘镜像输入**。当前轮只增加一个阶段性临时 no-libc RISC-V 用户 ELF fixture，建议先用汇编或极小 `no_std` Rust 产物，最终目标是直接通过 syscall 输出并退出；`make disk` 通过构造期 overlay 将该 fixture 放入 ext2 rootfs 的 `/sbin/init`。这个 `/sbin/init` overlay 不是长期正式首应用接口，也不要求新增正式 Makefile app 目标；等发行版 rootfs 中的 `/sbin/init`、`/bin/sh` 或等价 init 能作为首应用启动后，应删除该 fixture。首轮要求 ELF 足够小，能被当前 direct-block ext2 read path 读取，避免把 Ext2 indirect block 变成前置阻塞项。
3. **VFS 到 ELF 对象**。`UserBootPayload` 通过当前 `FsStruct.root` 和 VFS path API 打开并读取 `/sbin/init`；`ElfObject` 只支持 ELF64 little-endian RISC-V、静态可执行、`PT_LOAD` 段、`R/RW/RX` 权限、`.bss` 清零计划和 entry point 记录。`ElfObject.Preset` 只确认 ELF 类型受支持；`ElfObject.Setup` 解析 ELF 并形成 PT_LOAD 映射计划，实际消费该计划并建立用户映射事实归 `UserAddressSpace.Setup`；`ElfObject.Enable` 只确认 entry、stack、trap frame 等进入用户态条件已经满足。不引入独立 `ElfLoader` 对象，不支持解释器、动态链接、shared object、权限/xattr 和 shebang。
4. **用户地址空间和栈**。建立最小 `UserAddressSpace` 实例，消费 `ElfObject` 的 PT_LOAD 映射计划并建立 ELF segment mapping、`.bss` 清零、用户栈 mapping、用户页 `U` 权限和内核映射 `U=0` 的可观察事实；首个 `UserAddressSpace` 必须绑定到已到达 `PayloadPhase` 的 `KernelInitTask` 执行线，表示 kernel_init 用户态启动路径正在准备自己的第一个用户地址空间。切换前阶段分两层：先分配 backing pages、复制 ELF 文件内容、清零 `.bss`/stack 并建立 page-table-shaped view；再由 `UserAddressSpace.Enable` 分配真实 Sv39 用户页表页、安装低端用户 leaf PTE、共享 `SwapperVm` 高端 root entries、生成 satp token，并明确 prepared-but-not-current。该阶段仍不写 `satp`、不执行地址空间切换用 `sfence.vma`、不执行 `sret`。`SwapperVm` 继续代表内核共享地址空间实例，不改成普通多实例用户地址空间；多个 `UserAddressSpace` 实例只在低地址用户区独立，高地址内核区共享或引用 `SwapperVm`。RISC-V trap entry 所需内核入口映射必须在用户页表下可执行且保持 `U=0`，避免 U-mode trap 后无法进入 S-mode handler。
5. **U-mode 进入和 trap 返回**。先构造用户 trap frame，设置 `sepc=elf_entry`、用户 `sp`、`sstatus.SPP=U`、`SPIE=1`，并明确该 frame 只是下一轮统一 trap return 的输入；随后再经 `sret` 进入用户态。异常入口至少区分 user ecall、非法指令、页错误和其他 unexpected trap；unexpected trap 应记录诊断并终止用户进程或关机，不继续静默运行。
6. **最小 syscall 闭环**。首轮只实现 `write(fd=1/2, user_buf, len)` 和 `exit/exit_group(status)`；`write` 通过受限 `UserCopy` 从用户地址空间复制字节，再转发到现有 `printk`/serial console 输出。syscall 入口必须走既有 `SyscallException`，由 `SyscallException` 负责入口、来源检查、参数提取和分发表选择，`SyscallTable` 承载 `write` / `exit` / `exit_group` 等具体 action；此路径不是完整用户态标准 I/O，完整 fd table、`/dev/console`、TTY/N_TTY 和 line discipline 后续再补。
7. **验收与观测**。新增只读 checkpoint/KUnit 或 smoke 观测 `init ELF loaded`、`entered user mode`、`write syscall observed`、`exit status == 0`。当前 `/sbin/init` overlay fixture 注入阶段先用 smoke 验证真实 VFS/ext2 path 能读到 `/sbin/init` 且其 ELF header 符合 ELF64 little-endian RISC-V；进入 U-mode 后再补 checkpoint/KUnit 观测。验收命令至少包括 `make verify`、`make build APP=smoke`、`make run APP=smoke`、`make test` 和 `git diff --check`；是否增加 `make run APP=user-boot` 取决于后续是否确实需要独立 app 目标，当前不把它作为 fixture 注入阶段的硬前置。

首轮明确不做：

- 不运行 musl/glibc 静态大程序，除非先接受 Ext2 indirect block、更多 syscall 和 `brk/mmap` 成为前置任务。
- 不把当前阶段性 `/sbin/init` overlay fixture 当成长期启动应用模型；它只是打通 ELF 读取、映射和 U-mode 进入闭环的临时输入，最终由发行版 rootfs 中的 init/sh 替代。
- 不为当前 whole-disk ext2 镜像引入分区解析对象；`PartitionTable` / `BlockPartition` 等到磁盘镜像切换为带分区表时再建模。
- 不实现完整 `open/read/write/close` fd table；首轮 `write` 是 syscall 到 console 的窄路径。
- 不实现动态链接器、环境变量、完整 argv/auxv、权限检查、信号、fork/wait 或多用户进程调度。
- 不把 page cache 或 TTY/N_TTY 作为用户态 hello 的前置条件。

本阶段已完成 PLIC 驱动首轮建模和实现，并与 UART 驱动结合验证外部中断链已经建立；随后已完成 serial8250 console interrupt-driven TX 首轮切换。完整 RX、TTY runtime 和更完整 FIFO/并发策略后续单独展开。当前计划进度如下：

1. **已完成：规格确认 Linux-like 机制**。`irq-time-init` 规格已明确 PLIC 属于系统 irqchip，初始化位置对应 `init_IRQ() -> irqchip_init() -> of_irq_init()`；项目对应位置是 `IrqTimeInitPhase`，不是 `InitcallPhase` 的普通 `PlatformBus` driver probe；PLIC probe 由设备树 `interrupt-controller` node 和 compatible 匹配触发。
2. **已完成：规格拆出独立对象**。已拆出 `IrqChipInitTable`、`PlicDriver` 和 `Plic`：`PlicDriver.Preset` 表达 compatible/init callback 注册到 irqchip init table，`IrqChipInitTable.Setup` 表达 `of_irq_init()` 遍历 LDS section 并调用匹配的 PLIC init callback，`Plic.Preset` 表达 PLIC provider 的最小 setup 结果。
3. **已完成：coding 规格 LDS 段注册约束**。已规定 PLIC init entry 必须静态放入 irqchip init section，类似 initcall；`of_irq_init()` 实现必须遍历该 section，而不是运行时手动 push 注册项；匹配项覆盖当前 QEMU virt 的 `sifive,plic-1.0.0`，并保留 `riscv,plic0`。
4. **已完成：irqchip init table 骨架**。已增加 irqchip init entry 类型、`.irqchip.init` section、codegen/linker start/end 符号、遍历函数和 PLIC init entry；`make test` 的 `smoke.irq_time` 已验证 entry 来自 LDS section、compatible 被匹配、callback 经遍历被调用。
5. **已完成：PLIC setup 最小闭环**。已从设备树解析 PLIC node、`reg`、`riscv,ndev` 和 `interrupts-extended` 中的 boot hart supervisor external interrupt parent input；已用 runtime `ioremap`/`vmalloc` 以 system irqchip owner 映射 PLIC MMIO；已建立 external-input context 的 threshold、priority、source enable 基础状态；当前 `Plic` 已升级为最小 `Ready`，PLIC context 选择必须与 boot hart `riscv,cpu-intc` phandle 和 `SUPERVISOR_EXTERNAL_IRQ` 输入匹配。
6. **已完成：IRQ domain / source mapping**。已建立 `IrqDomain` 通用契约和 `PlicIrqDomain` 实例；`IrqTimeInitPhase` 在 `Plic.Ready` 后推进 domain 到 `Ready`；`Ns16550aPlatformDriver` probe 已解析 UART `interrupts`/`interrupt-parent`，确认父节点是 PLIC，并把 UART PLIC source 映射到 logical IRQ。`PlicIrqDomain` 仍只拥有 source -> logical IRQ 映射，不拥有 handler，也不启用 PLIC source；`PlicIrqMapping` 在建立 UART source mapping 时定义命名 source gate 并保持 closed，source enable action 继续 deferred；console 输出保持 polling。
7. **已完成：handler registry 与上下文约束**。已增加 `IrqHandlerRegistry` / `IrqAction` 和最小 `request_irq` 记录；`Ns16550aPlatformDriver` 在 UART logical IRQ 映射后登记最小 UART handler action；smoke/KUnit 覆盖 duplicate registration 拒绝、未映射 logical IRQ 拒绝、hardirq context requirement 和 source enable deferred。当前 handler 属于 IRQ core action，不能由 UART 私有表或测试代码直接执行，也不能声明 serial8250 interrupt-driven ready。
8. **已完成首轮：UART 外部中断链验证**。已建立只读 checkpoint KUnit observer：它只能读取 trace/counter/object facts 并通过受限 sink 输出诊断，不得调用 UART handler、root intc entry、PLIC claim/complete、`request_irq` 或 source-enable API，也不得修改 pending/claimed/enable 状态。当前 Linux-like dispatch contract 已落地为 `handle_arch_irq/root INTC external entry -> PLIC chained handler -> while claim != 0 -> PlicIrqDomain/generic IRQ dispatch -> registered UART action -> complete each claimed source -> zero claim exits loop`；外部传播链的两个 gate 已明确为命名 gate，root supervisor external input gate 在 `InterruptStream` external route 建立时定义，UART source gate 在 `PlicIrqMapping` 建立时定义；`UartExternalIrqEnable` 打开 PLIC UART source gate 和 root INTC supervisor external input gate，`UartInterruptChainProbe` 随后按 Linux-like 8250 THRI 形状设置 OUT2、启用 `UART_IER_THRI`，在 THRE 已置位状态下触发 UART THRE interrupt cycle，验证 `UART interrupt -> hart external interrupt -> root intc -> PLIC claim loop -> irq dispatch -> UART handler -> PLIC complete -> zero claim loop exit`，并确认本轮 claim/complete 与 zero-claim/loop-exit 成对闭合。提交 `3e03f27` 已完成该闭环，`make test` summary 为 `total=86 pass=86 fail=0`。该 probe 执行时 serial8250 console 仍保持 polling，避免在中断 gate 未确认前提前声明 interrupt-driven ready。
9. **已完成首轮：serial8250 interrupt-driven console TX**。已新增独立 `Serial8250ConsoleIrqTxProbe`：它在 `UartInterruptChainProbe` ready 后把 serial8250 console 从 polling/deferred 状态推进到 runtime interrupt-driven TX，通过公开 `printk` 前端提交探针输出，后端在本地中断保存/恢复 guard 内 enqueue CRLF 后 TX bytes 并 kick `UART_IER_THRI`，随后由真实 UART THRE interrupt 经 PLIC claim loop 和 IRQ core dispatch 调用 UART handler drain TX queue，最终观察 queue empty、THRI clear、PLIC complete 和 zero-claim loop exit。app smoke 仍只调用 printk 前端；KUnit 仍是旁路 observer。完整 RX、TTY runtime 和更完整 FIFO/并发策略继续 deferred。
10. **已完成当前轮：kernel printk console TX 稳定性**。按先对象关系、再 transitions/actions、最后补约束的顺序推进。第 1 步已确认职责边界：`Uart8250Port` 只表示 platform-probed 资源实例，`Serial8250RuntimePort` 承载 8250 IRQ-time IER/IIR/LSR、port lock 和 RX/TX handler 分发形状，`Serial8250Console` 只表示 printk real console entry，`TtyPort`/`TtyFlipBuffer`/`TtyXmitFifo` 分别表示最小 uart_state/tty_port 容器、RX flip-buffer staging 和普通 TTY write FIFO。第 2 步已定义 transition/action：`TtyPort.Setup/Enable`、`Serial8250RuntimePort.Setup/Enable`、`HandleInterrupt/ReceiveChars/TransmitChars/StartTx/StopTx`、`TtyFlipBuffer.InsertChar/Push` 和 `TtyXmitFifo.Enqueue/DequeueForTx`。第 3 步已完成单字符 RX loopback、固定小批量 RX loopback、ordinary TTY TX FIFO 的固定 byte enqueue/dequeue round-trip、ordinary TTY write 单 byte/固定小批量真实 IRQ 闭合、`Serial8250ConsoleBurstIrqTxProbe` 的多条 printk 连续输出闭合、`Serial8250RuntimePort::TransmitChars` 显式 `tx_loadsz` budget + `Serial8250ConsoleLongIrqTxProbe` 的单条长 printk 多轮 drain、`Serial8250ConsoleLongBurstIrqTxProbe` 的多条长 printk 按记录预算累加 drain，以及 `Serial8250ConsoleTxQuiesceProbe` 的 long-burst 后 no-spurious-IRQ 检查。该 quiesce probe 不提交新 printk，只观察 queue empty、THRI stopped、无额外 PLIC claim/IRQ dispatch/UART TX drain/TTY xmit mutation。固定 burst/long-burst/`Wtx04` 等用户可见测试 payload 已限定到 checkpoint/KUnit 测试构建；普通 `make run` 不再默认执行这些 TX/TTY payload probe。收尾规格已明确 app/smoke 只能走 `printk` 公开前端、backend 不可直调、TX drain 只能由真实 IRQ handler 推进、quiesce 后不得出现 spurious claim/dispatch/drain；file/stdout/stdin 和用户态 I/O 仍缓行。
11. **后续计划：printk TX 异常/压力边界**。下一轮若继续 kernel `printk` 主线，优先规格化 TX queue full 行为、overflow/drop/truncate/pending 事实、hardirq/irq-disabled 上下文中的 `printk` 允许边界、reentrant printk 处理，以及 handler 内 printk 是否 deferred。任何行为变更必须先有 model/coding 约束和独立 probe，不能通过现有 smoke/KUnit 隐式改变当前稳定路径。
12. **后续计划：serial8250 runtime 与 TTY 分层收口**。在 printk TX 基线稳定后，继续明确 `Serial8250RuntimePort`、`Serial8250Console`、`TtyPort`、`TtyFlipBuffer`、`TtyXmitFifo` 的长期职责边界，决定 ordinary TTY 何时从隔离验证对象升级为普通 I/O runtime。该轮仍优先保护 kernel printk console，不让 ordinary TTY TX/RX 反向污染 console TX queue。
13. **后续计划：用户态 I/O 延后展开**。file backend、stdout/stdin、`read/write` syscall、line discipline、N_TTY 和用户态标准输入输出机制暂列缓行；进入该阶段前必须先确认 printk console 和 serial8250 runtime 层职责稳定。

## 执行中计划：console 边界收口到 ioremap/vmalloc

按当前讨论确认的顺序逐项推进，每完成一项即更新本节状态并做一次提交：

1. **已完成：收口 console 测试边界**：app smoke 已移除直接操作 console registry / backend 的场景，只保留公开 `printk` 输出、无重复输出和用户可见 payload 结果；checkpoint/KUnit 只保留真实启动路径上的只读 observer，不再注册 app smoke 或需要 `&mut Context` 的 action-level handler。当前全量验收：`make test` 中 KUnit 11/11、app smoke 37/37、总计 49/49。
2. **已完成：补 EarlyCon / BootConsole / ConsoleRegistry 分层说明**：model/coding 已明确 EarlyCon 是早期 SBI backend，BootConsole 是 printk registry 中包装 EarlyCon 的 `CON_BOOT` entry，Serial8250Console 是真实 console entry，ConsoleRegistry 负责 route、handoff cursor 移交和 `keep_bootcon` 策略；drivers 只能请求注册，不拥有这些全局策略事实。验收：`make verify` 仍为 0 obligation。
3. **进行中：继续 ioremap/vmalloc 泛化**：规格边界已收口为 `VmallocAllocator` 负责 vmap VA 区间管理和每次 `map_page_range()` 的映射执行/`VmapMapping` 记录，`Ioremap` 负责设备物理资源来源和 MMIO 属性策略；实现侧已补齐单个 `VmapArea` 的 `vm_struct/vmap_area` metadata fact、每个 `VmapMapping` 的 record-created fact，当前已从首个 runtime mapping window 扩展到完整 `VMALLOC_START..VMALLOC_END` 页表 metadata 覆盖，并支持按需追加 L1/L0/PTE 页表页和稀疏 slot metadata；`VmapArea` / `VmapMapping` 记录已改为动态容器 backing，完整范围内跨 window mapping 支持，越过 `VMALLOC_END` 的范围和同一 busy area 上重复 mapping record 都会被拒绝。此前 `vmalloc_mapping.*` checkpoint/KUnit mutating handler 已移除；若要恢复 multi-record、unmap/free、ioremap/iounmap、MMIO attribute 等 action 行为测试，必须拆成 app smoke fixture 或先在 testing/coding 规格中定义显式 action-level probe capability，不得重新作为普通 checkpoint handler 注册。
4. **已完成首轮：补 MMIO 属性模型**：已区分 plain device、non-cache、write-combine 和 normal memory alias 策略；当前 RISC-V 实现只支持 plain device ioremap，对应 Linux-like `_PAGE_IOREMAP`/`PAGE_KERNEL_IO` 风格事实，non-cache/write-combine/normal memory alias 显式 deferred/unsupported，不把“能访问”写成“属性完整正确”。后续可在页表 PTE bit 模型完善后扩展真实属性编码。
5. **已完成首轮：实现 PLIC 驱动并验证 UART 外部中断链**：`Plic` 已作为独立系统 irqchip 对象建模；其 probe/setup 对应 Linux `init_IRQ() -> irqchip_init() -> of_irq_init()`，在本项目中落在 `IrqTimeInitPhase`，依赖 `DeviceTree.Ready` 和 PLIC `interrupt-controller` 节点，而不是后续 `PlatformBus` driver probe。规格层已表达 `Plic.Preset` 注册 compatible/init callback 到 irqchip init table，`of_irq_init()` 匹配 compatible 后调用 PLIC init；coding 层已表达该 table 由 LDS 段静态收集，类似 initcall 注册。当前已完成 PLIC irqdomain/source mapping、MMIO/ioremap、context threshold、source gate enable、claim/complete，并用 serial8250 IRQ resource 和最小 UART handler 验证 PLIC claim -> irq dispatch -> UART handler -> PLIC complete -> zero claim loop exit 链路；该链路 probe 执行时 console 仍保持 polling，后续第 6 项已完成 runtime TX interrupt-driven 切换。
6. **已完成首轮：serial8250 interrupt-driven console TX**：PLIC/UART 外部中断链首轮完成后，已把 runtime console TX 从 polling 扩展到 interrupt-driven：`printk` 提交 TX queue，THRI 中断驱动 UART handler drain queue，PLIC claim/complete 与 zero-claim loop exit 可观测闭合。完整 RX、TTY runtime 和更完整 FIFO/并发策略后续单独推进。
