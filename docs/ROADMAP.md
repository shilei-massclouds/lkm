# Roadmap

本文是项目唯一的优先级和任务状态入口。其它文档可以保留设计背景、约束、命令和专题方案，但不再维护独立的 P0/P1/P2 计划表。

## 优先级规则

- `P0`：当前最应优先推进，直接影响日常审阅或当前闭环质量。
- `P1`：近期应推进，通常依赖 `P0` 的结果或与其紧密相邻。
- `P2`：后续扩展项，应在当前闭环稳定后推进。

## 当前焦点

1. PLIC 驱动、UART 外部中断链和 serial8250 interrupt-driven console TX 当前轮已阶段性收尾：irqchip/irqdomain、PLIC 独立驱动对象、设备树驱动的 PLIC setup、platform IRQ resource 解析、serial8250 IRQ 绑定、handler registry、中断上下文约束、root INTC -> PLIC -> UART handler dispatch、一轮 UART THRE interrupt cycle 的 claim/complete/zero-claim 闭合，以及 `printk` 前端提交后由 THRI 中断驱动 UART handler drain TX queue 的 runtime TX 闭环均已验证。kernel `printk` console 稳定性已覆盖连续/批量 printk burst、Linux-like `tx_loadsz` 预算、单条长 printk 多轮 drain、多条长 printk long-burst，以及 long-burst 后的 `Serial8250ConsoleTxQuiesceProbe`；固定 burst/long-burst 和 ordinary TTY write `W`/`tx04` 等用户可见 TX/TTY 测试负载已经收口到 checkpoint/KUnit 测试构建，普通 `make run` 不再打印固定探针字节。
2. 下一阶段 P0 改为本项目与 Linux 6.12.37 的交叉验证，首轮聚焦 `drivers/irqchip/irq-sifive-plic.o` 二进制复用。参考源码位置为 `~/gitStudy/linux-6.12.37`；当前目标不是继续扩展功能，而是在 `arceos_ex` 中通过条件编译在原生 PLIC provider 与 Linux PLIC object provider 之间替换，建立 Linux 源码路径、当前 formal model、coding 规格、实现、checkpoint/trace/smoke/KUnit 之间的交叉引用和差异分类，把缺口明确归入“已覆盖、显式 deferred、规格缺口、实现缺口、刻意偏离、疑似 bug”。
3. 维持 `ioremap/vmalloc` 当前首轮成果：runtime page-table metadata 已覆盖完整 `VMALLOC_START..VMALLOC_END`，支持按需追加 L1/L0/PTE 页表页，`VmapArea` / `VmapMapping` 记录已改为动态容器 backing；更完整的 `vm_struct/vmap_area` 行为，例如空洞复用、增强树查找、lazy purge 和并发边界，降为后续补强，除非交叉验证发现其阻塞 IRQ/driver 路径的一致性。
4. serial8250 runtime RX/TTY/FIFO 补强继续保留为后续项。当前对象框架和 event/action 已确认，RX 单字符/批量 loopback、ordinary TTY TX FIFO 最小 enqueue/dequeue，以及 ordinary TTY write 经 `TtyXmitFifo -> StartTx/THRI -> handler TransmitChars` 的单 byte 和固定小批量真实 IRQ 闭合均已完成；后续是否继续展开 printk TX 异常/压力边界、TTY runtime 分层或用户态 I/O，应先经过 Linux 交叉验证结果排序。

## 下一阶段计划：Linux 6.12.37 PLIC 二进制复用

本节是当前 P0 的执行清单。每完成一项即更新本节状态并做一次提交；实现变更仍遵循先规格/约束、再代码、再验证的顺序。
`make test` 能够通过是判断阶段计划目标达成的重要验收手段。为实现 Linux PLIC object 对齐，当前部分规格、推导、实现和
测试都可以随执行过程调整，但调整必须服务于 Linux 公开接口和二进制复用目标，并在差异分类中记录清楚。

### 已确认原则

1. 条件编译选择的是 provider 文件组和链接对象，而不是在同一组 Rust 源码内部做大量细粒度裁剪。默认 provider 仍为 `native`；启用 Linux 路径时选择 `irq-sifive-plic.o + Linux ABI/adaptor shim`，并排除原生 PLIC 对同一硬件的 claim/complete/source enable 接管。
2. 首轮采用简单直接链接方案：`PLIC_PROVIDER=linux-object` 时直接把 `irq-sifive-plic.o` 作为 linker input 传入。静态库封装暂不作为首轮目标；后续若改为 `.a`，必须通过 `--whole-archive` 确保没有全局入口符号的对象文件也会被拉入最终内核。
3. `arceos_ex` 向 Linux PLIC object 的 RISC-V ABI 对齐。当前 Linux `irq-sifive-plic.o` 为 LP64/soft-float ABI，首轮应优先把 `arceos_ex` 切到 soft-float target，例如 `riscv64imac-unknown-none-elf` 或等价 custom target，而不是要求 Linux 对象适配当前 double-float ABI。
4. 上层机制直接向 Linux 形态收敛。Linux object 可见的 initcall section、platform driver、OF/fwnode、irq_domain、irq_chip、chained handler、per-CPU/cpumask 和 lifecycle callback 以 Linux contract 为准；`arceos_ex` 现有对象作为内部承载或 native provider 实现，不再保留一套厚转换后的私有上接口。
5. 下接口按 `nm -u` 逐符号“埋雷”补齐。函数先提供 ABI 正确的兜底实现，默认 panic/fail；全局变量先提供布局和符号名正确的最小对象。只有启动路径实际踩到且功能闭环必须的依赖，才逐项补真实语义；调试、打印、审计、ratelimit 等非关键能力可简化或标记 deferred。
6. 第三方 Linux 二进制对象放入 `impl/third_party/...`，首轮建议路径为 `impl/third_party/linux/6.12.37/riscv64-lp64/`，并保留 Linux 原始相对路径、构建配置和来源说明。
7. 进入下接口排雷阶段后，以已有原生 PLIC/IRQ/UART 近似等价实现为承载基础，优先做小规模 kernel 对齐和薄 shim 补充。若踩到必须新增正式对象、大功能缺失、或方向策略难以判断的问题，应暂停实现推进，先把问题归类并讨论后再继续。

9. **已完成首轮：补齐 `plic_probe()` 必须下接口语义**。已按 probe 实际路径补最小 OF/fwnode 属性读取、资源/ioremap、kmalloc/bitmap 分配、per-CPU/cpumask、hartid/cpuid、spinlock、irq domain instantiate、parent IRQ mapping、chained handler 记录、syscore/cpuhp 记录等受限语义；打印、ratelimit、调试和未进入 runtime 的 IRQ core callback 仍保持 deferred 或兜底 fail。当前验收结果表明 `plic_probe()` 能完成 PLIC 私有状态创建、context 选择、MMIO 映射和后续 IRQ core 注册调用。
10. **已完成第二轮：接入 Linux IRQ domain leaf flow / chained handler runtime 服务面**。`irq_domain_instantiate`、`irq_find_matching_fwspec`、`irq_create_mapping_affinity` 和 `__irq_set_handler` 已记录 domain/chained handler 注册事实；`handle_external_interrupt()` 在 `PLIC_PROVIDER=linux-object` 下进入 Linux `plic_handle_irq` claim loop。runtime 现在不再由 `generic_handle_domain_irq` 直接写 claim register 完成 source，而是按 Linux-shaped leaf flow 推进：首次遇到 hwirq 时调用 Linux `plic_irqdomain_ops.alloc`，由黑盒对象内部执行 `plic_irq_domain_translate -> plic_irqdomain_map -> irq_domain_set_info`，shim 只记录 Linux 对象交出的 `plic_chip`、`handle_fasteoi_irq` 和 leaf `irq_data/irq_desc` 视图；UART source gate 打开也会先确保 leaf mapping 已存在，再调用 Linux `plic_chip.irq_enable(irq_data)`，由黑盒对象打开 context enable bit 和 priority；随后显式执行 Linux PLIC UART chip callback exercise event，在同一 leaf `irq_data` 上调用 `irq_disable -> irq_enable -> irq_mask -> irq_unmask`，并临时设置 `IRQD_IRQ_DISABLED` 调用一次 `irq_eoi` 覆盖 Linux disabled EOI 特殊分支；同一 event 还临时开启 `PLIC_QUIRK_EDGE_INTERRUPT`，调用 Linux `irq_set_type(EDGE_RISING)` 让黑盒对象内联的 `irq_set_chip_handler_name_locked()` 把 leaf 切到 `plic_edge_chip`/`handle_edge_irq`，随后调用 `plic_edge_chip.irq_ack` 覆盖 edge ack 分支，再用 `irq_set_type(LEVEL_HIGH)` 恢复 `plic_chip`/`handle_fasteoi_irq` 和 enabled/unmasked 状态；同一组显式边界还覆盖 valid domain + unmapped hwirq 的失败返回，确认 `generic_handle_domain_irq` 返回 `-EINVAL` 并记录 source/errno，不经过非关键的 ratelimit/打印路径；`linux_plic.boundary_facts` checkpoint 只读观察这些 event 留下的计数事实。之后 `handle_fasteoi_irq` 先恢复 Rust `tp` 分发现有 `IrqHandlerRegistry` action，再切回 Linux `tp` 调用 `plic_chip.irq_eoi(irq_data)`，由 Linux `plic_irq_eoi` 写回 claim register 完成 source。`irq_get_irq_data` 已提供 parent/leaf 最小 `irq_data` 视图，`cpuhp_setup_state` 已按 `invoke=true` 调用 boot CPU startup，`enable_percpu_irq` 暂按 parent IRQ gate 的受限 no-op 处理；更完整 generic IRQ core 语义仍待后续排雷。`tp/thread_info` 边界已按 Linux object 运行期视图处理：进入 Linux object 前切到 Linux `thread_info`，返回 Rust dispatch 前恢复 Rust `tp`，Linux `tp` 激活期间关闭本地 SIE，避免嵌套中断把 Linux `tp` 泄漏到 Rust 执行上下文。
11. **进行中：让 native PLIC provider 收敛到同一上层 contract**。已先建立薄 `objects::plic_provider` contract，把 provider 后端 setup、domain translate/map/resolve、运行期 source gate enable、external interrupt handling、UART leaf chip/unmapped boundary exercise，以及 claim/dispatch/complete/zero-claim/loop-exit 观测计数收口到同一组 provider API；native provider 通过 Rust `Plic`/`PlicIrqDomain` 内部实现提供这些服务，Linux object provider 通过 `irq-sifive-plic.o` 和 shim 提供同名服务。上层 `InitcallPhase`、`PlicIrqDomain`、root external IRQ entry、`IrqDispatchTree`、`IrqHandlerRegistry`、serial8250 console TX 等使用者不再直接选择 native/Linux 分支。后续继续收敛 chip callback 的 provider contract，目标仍是条件编译只改变链接输入和 provider 文件组。
12. **已完成第二轮：建立分层验证闭环**。link-only、initcall 注册、platform match/probe、domain/chained 注册、leaf IRQ flow、chip callback 和 UART interrupt cycle 已有 checkpoint/KUnit/smoke 观察点，其中 `linux_plic.boundary_facts` 只读验证黑盒边界流程、交换数据以及 chip callback exercise event 留下的 `irq_enable/irq_disable/irq_mask/irq_unmask/disabled_irq_eoi/edge_irq_ack` callback 计数，并确认 edge 分支通过 Linux object 自身的 `irq_set_type` 切换到 `plic_edge_chip` 后再恢复 level/fasteoi；同一 checkpoint 还验证 unmapped hwirq fail boundary 的 `-EINVAL` 返回、source/errno 记录和 exercise success。`uart_irq_chain.observer_real_path` 已在 Linux PLIC object provider 下观察到 claim/dispatch/complete 计数闭合、zero-claim/loop-exit 成对闭合。当前验收命令 `make -C impl/arceos_ex run APP=smoke PLIC_PROVIDER=linux-object PROBE=linux-plic,uart-irq-chain` 通过，smoke 结果为 `passed=36 failed=0 total=36`。阶段收束时仍以 `make test` 通过作为重要验收；后续若 native provider contract 或更完整 generic IRQ core 接入导致失败，需要把失败明确归入下一项阻塞问题。

## 已完成计划：console/earlycon handoff

当前阶段已在 `PlatformBus -> ns16550a platform driver probe` 闭环上完成 Linux-like 的 early console 到真实 serial console 首轮交接。

1. 已对照 Linux `drivers/of/`、`drivers/tty/serial/8250/` 和 `kernel/printk/` 路径，确认 handoff 边界：`stdout-path` 选择 console 节点，OF platform population 生成 `PlatformDevice`，`ns16550a` driver probe 解析资源并注册 8250 port，真实 console 注册后由 printk 切换输出路径，除非 `keep_bootcon`。
2. 已补齐 model/coding 规格：明确 `EarlyCon`/`BootConsole`、`Serial8250Console`、`ConsoleRegistry`、`DeviceTree.stdout_path`、`Ns16550aPlatformDriver.Probe` 和 `ConsoleHandoff` 的对象关系、事件边界、`keep_bootcon` 策略和 handoff 后输出约束。
3. 已实现最小可观测闭环：读取 `stdout-path`，构造 `Uart8250Port`/`Serial8250Console`，在 `ns16550a` probe 成功且匹配 `stdout-path` 时触发 handoff。
4. 已实现 UART MMIO polling write：handoff 后 `printk::write_str()` 路由到 serial8250，通过 ioremap/vmalloc 建立的 `membase` 访问 UART，按 LSR/THR 轮询发送，当前不使用 SBI fallback。
5. 已补 smoke/KUnit：覆盖 `stdout-path` 命中后 handoff、非 `stdout-path` 设备不抢占 console、handoff 后 boot console 注销、`keep_bootcon` 保留 boot console、dummy non-match，以及 handoff 后 printk 路由和 UART polling 输出事实。
6. 已完成验收：`make verify`、`make build APP=smoke`、`make test` 均通过；handoff 首轮实现提交为 `ce59606` (`arceos-ex add serial8250 polling console`)，当前交接基线已推进到 `0316c1f` (`arceos-ex use dynamic vmalloc records`)。

## 已完成计划：PLIC 驱动与 UART 外部中断链

本阶段已完成 PLIC 驱动首轮建模和实现，并与 UART 驱动结合验证外部中断链已经建立；随后已完成 serial8250 console interrupt-driven TX 首轮切换。完整 RX、TTY runtime 和更完整 FIFO/并发策略后续单独展开。当前计划进度如下：

1. **已完成：规格确认 Linux-like 机制**。`irq-time-init` 规格已明确 PLIC 属于系统 irqchip，初始化位置对应 `init_IRQ() -> irqchip_init() -> of_irq_init()`；项目对应位置是 `IrqTimeInitPhase`，不是 `InitcallPhase` 的普通 `PlatformBus` driver probe；PLIC probe 由设备树 `interrupt-controller` node 和 compatible 匹配触发。
2. **已完成：规格拆出独立对象**。已拆出 `IrqChipInitTable`、`PlicDriver` 和 `Plic`：`PlicDriver.Preset` 表达 compatible/init callback 注册到 irqchip init table，`IrqChipInitTable.Setup` 表达 `of_irq_init()` 遍历 LDS section 并调用匹配的 PLIC init callback，`Plic.Preset` 表达 PLIC provider 的最小 setup 结果。
3. **已完成：coding 规格 LDS 段注册约束**。已规定 PLIC init entry 必须静态放入 irqchip init section，类似 initcall；`of_irq_init()` 实现必须遍历该 section，而不是运行时手动 push 注册项；匹配项覆盖当前 QEMU virt 的 `sifive,plic-1.0.0`，并保留 `riscv,plic0`。
4. **已完成：irqchip init table 骨架**。已增加 irqchip init entry 类型、`.irqchip.init` section、codegen/linker start/end 符号、遍历函数和 PLIC init entry；`make test` 的 `smoke.irq_time` 已验证 entry 来自 LDS section、compatible 被匹配、callback 经遍历被调用。
5. **已完成：PLIC setup 最小闭环**。已从设备树解析 PLIC node、`reg`、`riscv,ndev` 和 `interrupts-extended` 中的 boot hart supervisor external interrupt parent input；已用 runtime `ioremap`/`vmalloc` 以 system irqchip owner 映射 PLIC MMIO；已建立 external-input context 的 threshold、priority、source enable 基础状态；当前 `Plic` 已升级为最小 `Ready`，PLIC context 选择必须与 boot hart `riscv,cpu-intc` phandle 和 `SUPERVISOR_EXTERNAL_IRQ` 输入匹配。
6. **已完成：IRQ domain / source mapping**。已建立 `IrqDomain` 通用契约和 `PlicIrqDomain` 实例；`IrqTimeInitPhase` 在 `Plic.Ready` 后推进 domain 到 `Ready`；`Ns16550aPlatformDriver` probe 已解析 UART `interrupts`/`interrupt-parent`，确认父节点是 PLIC，并把 UART PLIC source 映射到 logical IRQ。`PlicIrqDomain` 仍只拥有 source -> logical IRQ 映射，不拥有 handler，也不启用 PLIC source；`PlicIrqMapping` 在建立 UART source mapping 时定义命名 source gate 并保持 closed，source enable action 继续 deferred；console 输出保持 polling。
7. **已完成：handler registry 与上下文约束**。已增加 `IrqHandlerRegistry` / `IrqAction` 和最小 `request_irq` 记录；`Ns16550aPlatformDriver` 在 UART logical IRQ 映射后登记最小 UART handler action；smoke/KUnit 覆盖 duplicate registration 拒绝、未映射 logical IRQ 拒绝、hardirq context requirement 和 source enable deferred。当前 handler 属于 IRQ core action，不能由 UART 私有表或测试代码直接执行，也不能声明 serial8250 interrupt-driven ready。
8. **已完成首轮：UART 外部中断链验证**。已建立只读 checkpoint KUnit observer：它只能读取 trace/counter/object facts 并通过受限 sink 输出诊断，不得调用 UART handler、root intc entry、PLIC claim/complete、`request_irq` 或 source-enable API，也不得修改 pending/claimed/enable 状态。当前 Linux-like dispatch contract 已落地为 `handle_arch_irq/root INTC external entry -> PLIC chained handler -> while claim != 0 -> PlicIrqDomain/generic IRQ dispatch -> registered UART action -> complete each claimed source -> zero claim exits loop`；外部传播链的两个 gate 已明确为命名 gate，root supervisor external input gate 在 `InterruptStream` external route 建立时定义，UART source gate 在 `PlicIrqMapping` 建立时定义；`UartExternalIrqEnable` 打开 PLIC UART source gate 和 root INTC supervisor external input gate，`UartInterruptChainProbe` 随后按 Linux-like 8250 THRI 形状设置 OUT2、启用 `UART_IER_THRI`，在 THRE 已置位状态下触发 UART THRE interrupt cycle，验证 `UART interrupt -> hart external interrupt -> root intc -> PLIC claim loop -> irq dispatch -> UART handler -> PLIC complete -> zero claim loop exit`，并确认本轮 claim/complete 与 zero-claim/loop-exit 成对闭合。提交 `3e03f27` 已完成该闭环，`make test` summary 为 `total=86 pass=86 fail=0`。该 probe 执行时 serial8250 console 仍保持 polling，避免在中断 gate 未确认前提前声明 interrupt-driven ready。
9. **已完成首轮：serial8250 interrupt-driven console TX**。已新增独立 `Serial8250ConsoleIrqTxProbe`：它在 `UartInterruptChainProbe` ready 后把 serial8250 console 从 polling/deferred 状态推进到 runtime interrupt-driven TX，通过公开 `printk` 前端提交探针输出，后端在本地中断保存/恢复 guard 内 enqueue CRLF 后 TX bytes 并 kick `UART_IER_THRI`，随后由真实 UART THRE interrupt 经 PLIC claim loop 和 IRQ core dispatch 调用 UART handler drain TX queue，最终观察 queue empty、THRI clear、PLIC complete 和 zero-claim loop exit。app smoke 仍只调用 printk 前端；KUnit 仍是旁路 observer。完整 RX、TTY runtime 和更完整 FIFO/并发策略继续 deferred。
10. **已完成当前轮：kernel printk console TX 稳定性**。按先对象关系、再 events/actions、最后补约束的顺序推进。第 1 步已确认职责边界：`Uart8250Port` 只表示 platform-probed 资源实例，`Serial8250RuntimePort` 承载 8250 IRQ-time IER/IIR/LSR、port lock 和 RX/TX handler 分发形状，`Serial8250Console` 只表示 printk real console entry，`TtyPort`/`TtyFlipBuffer`/`TtyXmitFifo` 分别表示最小 uart_state/tty_port 容器、RX flip-buffer staging 和普通 TTY write FIFO。第 2 步已定义 event/action：`TtyPort.Setup/Enable`、`Serial8250RuntimePort.Setup/Enable`、`HandleInterrupt/ReceiveChars/TransmitChars/StartTx/StopTx`、`TtyFlipBuffer.InsertChar/Push` 和 `TtyXmitFifo.Enqueue/DequeueForTx`。第 3 步已完成单字符 RX loopback、固定小批量 RX loopback、ordinary TTY TX FIFO 的固定 byte enqueue/dequeue round-trip、ordinary TTY write 单 byte/固定小批量真实 IRQ 闭合、`Serial8250ConsoleBurstIrqTxProbe` 的多条 printk 连续输出闭合、`Serial8250RuntimePort::TransmitChars` 显式 `tx_loadsz` budget + `Serial8250ConsoleLongIrqTxProbe` 的单条长 printk 多轮 drain、`Serial8250ConsoleLongBurstIrqTxProbe` 的多条长 printk 按记录预算累加 drain，以及 `Serial8250ConsoleTxQuiesceProbe` 的 long-burst 后 no-spurious-IRQ 检查。该 quiesce probe 不提交新 printk，只观察 queue empty、THRI stopped、无额外 PLIC claim/IRQ dispatch/UART TX drain/TTY xmit mutation。固定 burst/long-burst/`Wtx04` 等用户可见测试 payload 已限定到 checkpoint/KUnit 测试构建；普通 `make run` 不再默认执行这些 TX/TTY payload probe。收尾规格已明确 app/smoke 只能走 `printk` 公开前端、backend 不可直调、TX drain 只能由真实 IRQ handler 推进、quiesce 后不得出现 spurious claim/dispatch/drain；file/stdout/stdin 和用户态 I/O 仍缓行。
11. **后续计划：printk TX 异常/压力边界**。下一轮若继续 kernel `printk` 主线，优先规格化 TX queue full 行为、overflow/drop/truncate/pending 事实、hardirq/irq-disabled 上下文中的 `printk` 允许边界、reentrant printk 处理，以及 handler 内 printk 是否 deferred。任何行为变更必须先有 model/coding 约束和独立 probe，不能通过现有 smoke/KUnit 隐式改变当前稳定路径。
12. **后续计划：serial8250 runtime 与 TTY 分层收口**。在 printk TX 基线稳定后，继续明确 `Serial8250RuntimePort`、`Serial8250Console`、`TtyPort`、`TtyFlipBuffer`、`TtyXmitFifo` 的长期职责边界，决定 ordinary TTY 何时从隔离验证对象升级为普通 I/O runtime。该轮仍优先保护 kernel printk console，不让 ordinary TTY TX/RX 反向污染 console TX queue。
13. **后续计划：用户态 I/O 延后展开**。file backend、stdout/stdin、`read/write` syscall、line discipline、N_TTY 和用户态标准输入输出机制暂列缓行；进入该阶段前必须先确认 printk console 和 serial8250 runtime 层职责稳定。

## 执行中计划：console 边界收口到 ioremap/vmalloc

按当前讨论确认的顺序逐项推进，每完成一项即更新本节状态并做一次提交：

1. **已完成：收口 console 测试边界**：app smoke 已移除直接操作 console registry / backend 的场景，只保留公开 `printk` 输出、无重复输出和用户可见 payload 结果；default handoff/idempotent、dummy non-match、non-stdout 和 `keep_bootcon` 已迁到 checkpoint KUnit/action-level handler。当前全量验收：`make test` 中 KUnit 49/49、app smoke 36/36，总计 86/86。
2. **已完成：补 EarlyCon / BootConsole / ConsoleRegistry 分层说明**：model/coding 已明确 EarlyCon 是早期 SBI backend，BootConsole 是 printk registry 中包装 EarlyCon 的 `CON_BOOT` entry，Serial8250Console 是真实 console entry，ConsoleRegistry 负责 route、handoff cursor 移交和 `keep_bootcon` 策略；drivers 只能请求注册，不拥有这些全局策略事实。验收：`make verify` 仍为 0 obligation。
3. **进行中：继续 ioremap/vmalloc 泛化**：规格边界已收口为 `VmallocAllocator` 负责 vmap VA 区间管理和每次 `map_page_range()` 的映射执行/`VmapMapping` 记录，`Ioremap` 负责设备物理资源来源和 MMIO 属性策略；实现侧已补齐单个 `VmapArea` 的 `vm_struct/vmap_area` metadata fact、每个 `VmapMapping` 的 record-created fact，并新增 `vmalloc_mapping.multi_record` KUnit 覆盖多次 `map_page_range()` 产生多个独立 mapping record；已补 `UnmapPageRange`/`FreeVmArea` 规格和 `vmalloc_mapping.unmap_free` KUnit 覆盖先 unmap 后 free、重复 unmap/free 拒绝；`Ioremap.iounmap()` 已接到这条 vmalloc/vmap teardown 路径，新增 KUnit 覆盖 cookie retired 与重复 iounmap 拒绝；当前已从首个 runtime mapping window 扩展到完整 `VMALLOC_START..VMALLOC_END` 页表 metadata 覆盖，并支持按需追加 L1/L0/PTE 页表页和稀疏 slot metadata；`VmapArea` / `VmapMapping` 记录已改为动态容器 backing，完整范围内跨 window mapping 支持，越过 `VMALLOC_END` 的范围和同一 busy area 上重复 mapping record 都会被拒绝。
4. **已完成首轮：补 MMIO 属性模型**：已区分 plain device、non-cache、write-combine 和 normal memory alias 策略；当前 RISC-V 实现只支持 plain device ioremap，对应 Linux-like `_PAGE_IOREMAP`/`PAGE_KERNEL_IO` 风格事实，non-cache/write-combine/normal memory alias 显式 deferred/unsupported，不把“能访问”写成“属性完整正确”。后续可在页表 PTE bit 模型完善后扩展真实属性编码。
5. **已完成首轮：实现 PLIC 驱动并验证 UART 外部中断链**：`Plic` 已作为独立系统 irqchip 对象建模；其 probe/setup 对应 Linux `init_IRQ() -> irqchip_init() -> of_irq_init()`，在本项目中落在 `IrqTimeInitPhase`，依赖 `DeviceTree.Ready` 和 PLIC `interrupt-controller` 节点，而不是后续 `PlatformBus` driver probe。规格层已表达 `Plic.Preset` 注册 compatible/init callback 到 irqchip init table，`of_irq_init()` 匹配 compatible 后调用 PLIC init；coding 层已表达该 table 由 LDS 段静态收集，类似 initcall 注册。当前已完成 PLIC irqdomain/source mapping、MMIO/ioremap、context threshold、source gate enable、claim/complete，并用 serial8250 IRQ resource 和最小 UART handler 验证 PLIC claim -> irq dispatch -> UART handler -> PLIC complete -> zero claim loop exit 链路；该链路 probe 执行时 console 仍保持 polling，后续第 6 项已完成 runtime TX interrupt-driven 切换。
6. **已完成首轮：serial8250 interrupt-driven console TX**：PLIC/UART 外部中断链首轮完成后，已把 runtime console TX 从 polling 扩展到 interrupt-driven：`printk` 提交 TX queue，THRI 中断驱动 UART handler drain queue，PLIC claim/complete 与 zero-claim loop exit 可观测闭合。完整 RX、TTY runtime 和更完整 FIFO/并发策略后续单独推进。
