# Roadmap

本文是项目唯一的优先级和任务状态入口。其它文档可以保留设计背景、约束、命令和专题方案，但不再维护独立的 P0/P1/P2 计划表。

## 优先级规则

- `P0`：当前最应优先推进，直接影响日常审阅或当前闭环质量。
- `P1`：近期应推进，通常依赖 `P0` 的结果或与其紧密相邻。
- `P2`：后续扩展项，应在当前闭环稳定后推进。

## 当前焦点

1. PLIC 驱动、UART 外部中断链和 serial8250 interrupt-driven console TX 首轮已完成：irqchip/irqdomain、PLIC 独立驱动对象、设备树驱动的 PLIC setup、platform IRQ resource 解析、serial8250 IRQ 绑定、handler registry、中断上下文约束、root INTC -> PLIC -> UART handler dispatch、一轮 UART THRE interrupt cycle 的 claim/complete/zero-claim 闭合，以及 `printk` 前端提交后由 THRI 中断驱动 UART handler drain TX queue 的 runtime TX 闭环均已验证。serial8250 runtime RX 首轮单字符 loopback 和有限批量 loopback 已进入当前 P0 闭环；更完整 TTY runtime、普通 TTY write FIFO、line discipline 和更完整并发策略仍待后续展开。
2. 维持 `ioremap/vmalloc` 当前首轮成果：runtime page-table metadata 已覆盖完整 `VMALLOC_START..VMALLOC_END`，支持按需追加 L1/L0/PTE 页表页，`VmapArea` / `VmapMapping` 记录已改为动态容器 backing；更完整的 `vm_struct/vmap_area` 行为，例如空洞复用、增强树查找、lazy purge 和并发边界，降为后续补强，除非阻塞后续 IRQ/driver 路径。
3. 下一轮 P0 已确定为 serial8250 runtime RX/TTY/FIFO 补强，并按三步推进：先固定对象职责边界与层次/协作关系，再定义 events/actions，最后补必要的 model/coding 约束。当前第 1 步对象框架已确认：`Uart8250Port` 保持资源实例，新增/明确 `Serial8250RuntimePort` 作为 8250 运行期行为层，`Serial8250Console` 只承担 printk console entry，`TtyPort`、`TtyFlipBuffer`、`TtyXmitFifo` 分别承载最小 TTY 容器、RX staging 和普通 TTY TX FIFO；第 2 步已定义这些对象的 `Setup/Enable` 与 `HandleInterrupt/ReceiveChars/TransmitChars/StartTx/StopTx`、`InsertChar/Push`、`Enqueue/DequeueForTx` 等 event/action；第 3 步已完成 RX 单字符/批量 loopback、ordinary TTY TX FIFO 的最小 enqueue/dequeue 观察边界，以及 ordinary TTY write 经 `TtyXmitFifo -> StartTx/THRI -> handler TransmitChars` 的单 byte 真实 IRQ 闭合。当前继续补 `TtyWriteBatchRuntimeTxProbe` 固定小批量轮次，验证 batch enqueue/dequeue/runtime drain 增量、queue empty、last byte、无 overflow/underflow，并继续要求它不复用 printk console TX queue。

## 已完成计划：console/earlycon handoff

当前阶段已在 `PlatformBus -> ns16550a platform driver probe` 闭环上完成 Linux-like 的 early console 到真实 serial console 首轮交接。

1. 已对照 Linux `drivers/of/`、`drivers/tty/serial/8250/` 和 `kernel/printk/` 路径，确认 handoff 边界：`stdout-path` 选择 console 节点，OF platform population 生成 `PlatformDevice`，`ns16550a` driver probe 解析资源并注册 8250 port，真实 console 注册后由 printk 切换输出路径，除非 `keep_bootcon`。
2. 已补齐 model/coding 规格：明确 `EarlyCon`/`BootConsole`、`Serial8250Console`、`ConsoleRegistry`、`DeviceTree.stdout_path`、`Ns16550aPlatformDriver.Probe` 和 `ConsoleHandoff` 的对象关系、事件边界、`keep_bootcon` 策略和 handoff 后输出约束。
3. 已实现最小可观测闭环：读取 `stdout-path`，构造 `Uart8250Port`/`Serial8250Console`，在 `ns16550a` probe 成功且匹配 `stdout-path` 时触发 handoff。
4. 已实现 UART MMIO polling write：handoff 后 `printk::write_str()` 路由到 serial8250，通过 ioremap/vmalloc 建立的 `membase` 访问 UART，按 LSR/THR 轮询发送，当前不使用 SBI fallback。
5. 已补 smoke/KUnit：覆盖 `stdout-path` 命中后 handoff、非 `stdout-path` 设备不抢占 console、handoff 后 boot console 注销、`keep_bootcon` 保留 boot console、dummy non-match，以及 handoff 后 printk 路由和 UART polling 输出事实。
6. 已完成验收：`make verify`、`make build APP=smoke`、`make test` 均通过；handoff 首轮实现提交为 `ce59606` (`arceos-ex add serial8250 polling console`)，当前交接基线已推进到 `0316c1f` (`arceos-ex use dynamic vmalloc records`)。

## 已完成计划：PLIC 驱动与 UART 外部中断链

本阶段已完成 PLIC 驱动首轮建模和实现，并与 UART 驱动结合验证外部中断链已经建立；随后已完成 serial8250 console interrupt-driven TX 首轮切换。完整 RX、TTY runtime 和更完整 FIFO/并发策略后续单独展开。当前计划进度如下：

1. **已完成：规格确认 Linux-like 机制**。`irq-time-init` 规格已明确 PLIC 属于系统 irqchip，初始化位置对应 `init_IRQ() -> irqchip_init() -> of_irq_init()`；项目对应位置是 `IrqTimeInitPhase`，不是 `InitcallPhase` 的普通 `PlatformBus` driver probe；PLIC probe 由设备树 `interrupt-controller` node 和 compatible 匹配触发。
2. **已完成：规格拆出独立对象**。已拆出 `IrqChipInitTable`、`PlicDriver` 和 `Plic`：`PlicDriver.Preset` 表达 compatible/init callback 注册到 irqchip init table，`IrqChipInitTable.Setup` 表达 `of_irq_init()` 遍历 LDS section 并调用匹配的 PLIC init callback，`Plic.Preset` 表达 PLIC provider 的最小 setup 结果。
3. **已完成：coding 规格 LDS 段注册约束**。已规定 PLIC init entry 必须静态放入 irqchip init section，类似 initcall；`of_irq_init()` 实现必须遍历该 section，而不是运行时手动 push 注册项；匹配项覆盖当前 QEMU virt 的 `sifive,plic-1.0.0`，并保留 `riscv,plic0`。
4. **已完成：irqchip init table 骨架**。已增加 irqchip init entry 类型、`.irqchip.init` section、codegen/linker start/end 符号、遍历函数和 PLIC init entry；`make test` 的 `smoke.irq_time` 已验证 entry 来自 LDS section、compatible 被匹配、callback 经遍历被调用。
5. **已完成：PLIC setup 最小闭环**。已从设备树解析 PLIC node、`reg`、`riscv,ndev` 和 `interrupts-extended` 中的 boot hart supervisor external interrupt parent input；已用 runtime `ioremap`/`vmalloc` 以 system irqchip owner 映射 PLIC MMIO；已建立 external-input context 的 threshold、priority、source enable 基础状态；当前 `Plic` 已升级为最小 `Ready`，PLIC context 选择必须与 boot hart `riscv,cpu-intc` phandle 和 `SUPERVISOR_EXTERNAL_IRQ` 输入匹配。
6. **已完成：IRQ domain / source mapping**。已建立 `IrqDomain` 通用契约和 `PlicIrqDomain` 实例；`IrqTimeInitPhase` 在 `Plic.Ready` 后推进 domain 到 `Ready`；`Ns16550aPlatformDriver` probe 已解析 UART `interrupts`/`interrupt-parent`，确认父节点是 PLIC，并把 UART PLIC source 映射到 logical IRQ。`PlicIrqDomain` 仍只拥有 source -> logical IRQ 映射，不拥有 handler，也不启用 PLIC source；`PlicIrqMapping` 在建立 UART source mapping 时定义命名 source gate 并保持 closed，source enable action 继续 deferred；console 输出保持 polling。
7. **已完成：handler registry 与上下文约束**。已增加 `IrqHandlerRegistry` / `IrqAction` 和最小 `request_irq` 记录；`Ns16550aPlatformDriver` 在 UART logical IRQ 映射后登记最小 UART handler action；smoke/KUnit 覆盖 duplicate registration 拒绝、未映射 logical IRQ 拒绝、hardirq context requirement 和 source enable deferred。当前 handler 属于 IRQ core action，不能由 UART 私有表或测试代码直接执行，也不能声明 serial8250 interrupt-driven ready。
8. **已完成首轮：UART 外部中断链验证**。已建立只读 checkpoint KUnit observer：它只能读取 trace/counter/object facts 并通过受限 sink 输出诊断，不得调用 UART handler、root intc entry、PLIC claim/complete、`request_irq` 或 source-enable API，也不得修改 pending/claimed/enable 状态。当前 Linux-like dispatch contract 已落地为 `handle_arch_irq/root INTC external entry -> PLIC chained handler -> while claim != 0 -> PlicIrqDomain/generic IRQ dispatch -> registered UART action -> complete each claimed source -> zero claim exits loop`；外部传播链的两个 gate 已明确为命名 gate，root supervisor external input gate 在 `InterruptStream` external route 建立时定义，UART source gate 在 `PlicIrqMapping` 建立时定义；`UartExternalIrqEnable` 打开 PLIC UART source gate 和 root INTC supervisor external input gate，`UartInterruptChainProbe` 随后按 Linux-like 8250 THRI 形状设置 OUT2、启用 `UART_IER_THRI`，在 THRE 已置位状态下触发 UART THRE interrupt cycle，验证 `UART interrupt -> hart external interrupt -> root intc -> PLIC claim loop -> irq dispatch -> UART handler -> PLIC complete -> zero claim loop exit`，并确认本轮 claim/complete 与 zero-claim/loop-exit 成对闭合。提交 `3e03f27` 已完成该闭环，`make test` summary 为 `total=86 pass=86 fail=0`。该 probe 执行时 serial8250 console 仍保持 polling，避免在中断 gate 未确认前提前声明 interrupt-driven ready。
9. **已完成首轮：serial8250 interrupt-driven console TX**。已新增独立 `Serial8250ConsoleIrqTxProbe`：它在 `UartInterruptChainProbe` ready 后把 serial8250 console 从 polling/deferred 状态推进到 runtime interrupt-driven TX，通过公开 `printk` 前端提交探针输出，后端在本地中断保存/恢复 guard 内 enqueue CRLF 后 TX bytes 并 kick `UART_IER_THRI`，随后由真实 UART THRE interrupt 经 PLIC claim loop 和 IRQ core dispatch 调用 UART handler drain TX queue，最终观察 queue empty、THRI clear、PLIC complete 和 zero-claim loop exit。app smoke 仍只调用 printk 前端；KUnit 仍是旁路 observer。完整 RX、TTY runtime 和更完整 FIFO/并发策略继续 deferred。
10. **进行中：serial8250 runtime RX/TTY/FIFO 规格**。按先对象关系、再 events/actions、最后补约束的顺序推进。第 1 步已确认职责边界：`Uart8250Port` 只表示 platform-probed 资源实例，`Serial8250RuntimePort` 承载 8250 IRQ-time IER/IIR/LSR、port lock 和 RX/TX handler 分发形状，`Serial8250Console` 只表示 printk real console entry，`TtyPort`/`TtyFlipBuffer`/`TtyXmitFifo` 分别表示最小 uart_state/tty_port 容器、RX flip-buffer staging 和普通 TTY write FIFO。第 2 步已定义 event/action：`TtyPort.Setup/Enable`、`Serial8250RuntimePort.Setup/Enable`、`HandleInterrupt/ReceiveChars/TransmitChars/StartTx/StopTx`、`TtyFlipBuffer.InsertChar/Push` 和 `TtyXmitFifo.Enqueue/DequeueForTx`。第 3 步已完成单字符 RX loopback、固定小批量 RX loopback、ordinary TTY TX FIFO 的固定 byte enqueue/dequeue round-trip 和隔离事实，以及 ordinary TTY write 接 runtime TX/THRI 的单 byte 闭合：`TtyWriteRuntimeTxProbe` 通过 `TtyXmitFifo` enqueue 固定 byte，经 `Serial8250RuntimePort.StartTx` 设置 THRI，让真实 PLIC/IRQ/handler 调用 `TransmitChars` drain FIFO 并清 THRI，同时验证不调用 printk、不修改 serial8250 console TX queue、queue empty、last byte 和 claim/complete/zero-claim 闭合。当前继续补 ordinary TTY write 固定小批量轮次：`TtyWriteBatchRuntimeTxProbe` 在单 byte 闭合 Ready 之后 enqueue 固定 batch，经同一条 THRI/PLIC/IRQ/runtime handler 链 drain FIFO，验收 batch enqueue/dequeue/runtime drain 增量匹配、bounded drain、queue empty、last byte、无 overflow/underflow、本地中断 guard 和 printk console TX queue 不变。

## 执行中计划：console 边界收口到 ioremap/vmalloc

按当前讨论确认的顺序逐项推进，每完成一项即更新本节状态并做一次提交：

1. **已完成：收口 console 测试边界**：app smoke 已移除直接操作 console registry / backend 的场景，只保留公开 `printk` 输出、无重复输出和用户可见 payload 结果；default handoff/idempotent、dummy non-match、non-stdout 和 `keep_bootcon` 已迁到 checkpoint KUnit/action-level handler。当前全量验收：`make test` 中 KUnit 49/49、app smoke 36/36，总计 86/86。
2. **已完成：补 EarlyCon / BootConsole / ConsoleRegistry 分层说明**：model/coding 已明确 EarlyCon 是早期 SBI backend，BootConsole 是 printk registry 中包装 EarlyCon 的 `CON_BOOT` entry，Serial8250Console 是真实 console entry，ConsoleRegistry 负责 route、handoff cursor 移交和 `keep_bootcon` 策略；drivers 只能请求注册，不拥有这些全局策略事实。验收：`make verify` 仍为 0 obligation。
3. **进行中：继续 ioremap/vmalloc 泛化**：规格边界已收口为 `VmallocAllocator` 负责 vmap VA 区间管理和每次 `map_page_range()` 的映射执行/`VmapMapping` 记录，`Ioremap` 负责设备物理资源来源和 MMIO 属性策略；实现侧已补齐单个 `VmapArea` 的 `vm_struct/vmap_area` metadata fact、每个 `VmapMapping` 的 record-created fact，并新增 `vmalloc_mapping.multi_record` KUnit 覆盖多次 `map_page_range()` 产生多个独立 mapping record；已补 `UnmapPageRange`/`FreeVmArea` 规格和 `vmalloc_mapping.unmap_free` KUnit 覆盖先 unmap 后 free、重复 unmap/free 拒绝；`Ioremap.iounmap()` 已接到这条 vmalloc/vmap teardown 路径，新增 KUnit 覆盖 cookie retired 与重复 iounmap 拒绝；当前已从首个 runtime mapping window 扩展到完整 `VMALLOC_START..VMALLOC_END` 页表 metadata 覆盖，并支持按需追加 L1/L0/PTE 页表页和稀疏 slot metadata；`VmapArea` / `VmapMapping` 记录已改为动态容器 backing，完整范围内跨 window mapping 支持，越过 `VMALLOC_END` 的范围和同一 busy area 上重复 mapping record 都会被拒绝。
4. **已完成首轮：补 MMIO 属性模型**：已区分 plain device、non-cache、write-combine 和 normal memory alias 策略；当前 RISC-V 实现只支持 plain device ioremap，对应 Linux-like `_PAGE_IOREMAP`/`PAGE_KERNEL_IO` 风格事实，non-cache/write-combine/normal memory alias 显式 deferred/unsupported，不把“能访问”写成“属性完整正确”。后续可在页表 PTE bit 模型完善后扩展真实属性编码。
5. **已完成首轮：实现 PLIC 驱动并验证 UART 外部中断链**：`Plic` 已作为独立系统 irqchip 对象建模；其 probe/setup 对应 Linux `init_IRQ() -> irqchip_init() -> of_irq_init()`，在本项目中落在 `IrqTimeInitPhase`，依赖 `DeviceTree.Ready` 和 PLIC `interrupt-controller` 节点，而不是后续 `PlatformBus` driver probe。规格层已表达 `Plic.Preset` 注册 compatible/init callback 到 irqchip init table，`of_irq_init()` 匹配 compatible 后调用 PLIC init；coding 层已表达该 table 由 LDS 段静态收集，类似 initcall 注册。当前已完成 PLIC irqdomain/source mapping、MMIO/ioremap、context threshold、source gate enable、claim/complete，并用 serial8250 IRQ resource 和最小 UART handler 验证 PLIC claim -> irq dispatch -> UART handler -> PLIC complete -> zero claim loop exit 链路；该链路 probe 执行时 console 仍保持 polling，后续第 6 项已完成 runtime TX interrupt-driven 切换。
6. **已完成首轮：serial8250 interrupt-driven console TX**：PLIC/UART 外部中断链首轮完成后，已把 runtime console TX 从 polling 扩展到 interrupt-driven：`printk` 提交 TX queue，THRI 中断驱动 UART handler drain queue，PLIC claim/complete 与 zero-claim loop exit 可观测闭合。完整 RX、TTY runtime 和更完整 FIFO/并发策略后续单独推进。
